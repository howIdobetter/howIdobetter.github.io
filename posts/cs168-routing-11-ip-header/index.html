IP 首部的设计目标

回想一下，像 IP 这样的协议（protocol）由语法（syntax）和语义（semantics）组成。语法决定 IP 首部（IP header）中有哪些字段，语义则决定如何处理这些字段。

另外，回想一下，IP 数据包（IP packet）由首部和有效载荷（payload）组成。首部包含 IP 协议能够处理的相关元数据（metadata）。有效载荷包含所有将被向上传递给更高层协议的数据，IP 协议不会解析它。

最后，回想一下，当我们沿协议栈（stack）向下移动时，会添加首部；当我们沿协议栈向上传递数据包时，则会剥离首部。两端的终端主机（end host）和每一台中间路由器（router）都会处理 IP 首部。

IP 首部应当尽可能小。通过互联网发送的每个数据包都需要附带 IP 首部，因此，即便只将 IP 首部增大一个字节，也会显著增加整个互联网的带宽用量。

IP 首部应当尽可能简单。每台路由器和终端主机都必须处理发送和接收的 IP 数据包，因此，处理起来很复杂的首部会拖慢整个互联网。理想情况下，我们希望完全用硬件处理首部，所以不能假定处理这个首部时能够使用通用 CPU 操作。

IP 首部字段

IP 协议需要完成四件事：

所有设备（终端主机、路由器）都需要能够解析（parse）数据包，并理解各个比特的含义。为此，首部会包含 IP 版本（4 位值）、首部长度（4 位值，以 4 字节字为单位；由于 IP 首部长度不固定，因此需要该字段）和数据包长度（16 位值，以字节为单位）。

路由器（而非终端主机）需要将数据包转发（forward）给下一台路由器。为此，首部会包含目的 IP 地址（32 位值）。

终端主机（而非路由器）需要将数据包向上传递给更高层。为此，首部会包含协议号（8 位值），它告诉我们应当使用哪个第 4 层协议（TCP 或 UDP）来处理有效载荷。例如，协议号 6 表示使用 TCP 协议读取剩余的有效载荷（把有效载荷最前面的比特作为 TCP 首部读取，依此类推）。协议号 17 对应 UDP 协议。

终端主机和路由器需要能够向源端发回回复。为此，首部会包含源 IP 地址（32 位值）。

IP 错误处理

终端主机和路由器还需要能够指明问题或特殊情况，以便在数据包需要额外处理时加以说明。

IP 数据包可能陷入环路（例如，路由协议尚未收敛时）。一种可能的做法是让数据包无限循环，直到路由收敛；但数据包转发发生在纳秒尺度，而路由收敛发生在毫秒或秒尺度。让数据包一直循环到路由收敛可能耗时很长，并浪费大量带宽。为防止无限循环，IP 首部中设有生存时间（time to live, TTL）（8 位值），每经过一跳便将其减 1。如果 TTL 变为 0，数据包就会被丢弃，并向源端发回一条错误消息。（IP 规范要求发送这条错误消息，但实践中并不总会发送。）

IP 数据包可能损坏（例如，线路上的比特可能因电气过程而发生错误）。为了检测损坏，IP 首部包含校验和（checksum）（16 位值）；如果校验和不正确，就丢弃数据包。

请注意，IP 校验和只针对 IP 首部计算。校验和只能检测 IP 首部中的错误，不能检测 IP 有效载荷中的错误。这体现了端到端原则（end-to-end principle）：我们要求由终端主机而不是中间路由器检查有效载荷。

每台路由器都会更新 IP 校验和，因为 TTL 会变化，校验和必须重新计算。一种可能的替代设计是计算校验和时排除 TTL，从而省去路由器的额外工作。

IP 数据包对于某条特定链路来说可能过大。每条链路都有一个最大传输单元（maximum transmission unit, MTU），表示该链路能够作为一个整体承载的最大数据包大小（以字节为单位）。例如，链路在沿线路发送数据包中的比特时，用于暂存该数据包的内存可能有限。

终端主机不知道哪些链路会承载这个数据包，因此可能发送一个对其中某条链路来说过大的数据包。为解决这个问题，路由器可以进行分片（fragmentation），把数据包拆分成多个分片；链路另一端的路由器必须重新组装这些分片，以恢复原始数据包。首部中的标识（16 位）、标志（3 位）和偏移量（13 位）字段用于实现分片。

分片可以在硬件中实现（例如，路由器可以快速对数据包进行分片，而无需将数据包转交特殊处理），但它会带来额外开销。现代互联网会尽可能避免分片。例如，我们会尽量将 MTU 标准化（现代标准之一是 1500 字节）。

IP 的早期设计者没有完全接受尽力而为（best-effort）设计，并认为允许应用程序根据自身需求发送不同类型的数据包或许会很有用。为实现这一点，IP 首部中设有服务类型（Type of Service, ToS）比特（8 位值），可用来请求不同形式的数据包交付。例如，可以将某些数据包标记为对时延敏感或高优先级。多年来，这些比特经过重新定义，用于表示不同的协议，ToS 已不再以最初的形式存在。如今，这些比特表示某种优先级概念。使用这些比特的协议示例包括区分服务代码点（Differentiated Services Code Point, DSCP）和显式拥塞通知（Explicit Congestion Notification, ECN）；前者定义某些流量类别，后者将有助于处理流量拥塞（稍后讨论）。

在最初的 IP 设计中，可以向 IP 首部添加额外的选项比特，请求对数据包进行更高级的处理。例如，发送方可以请求路由器记录数据包正在经过的路径（例如用于诊断）。发送方可以在数据包首部中加入源路由，并强制数据包沿某条特定路径传输。数据包首部也可以包含时间戳。在现代实现中，这些选项几乎总是被禁用，因为它们会导致实现不必要地复杂，并增加数据包处理开销。例如，这些选项会迫使 IP 首部采用可变长度，而可变长度首部比固定长度首部更难处理。

IPv6 首部的变化

IPv6 的提出源于这样一种担忧：32 位 IPv4 地址最终会耗尽。IPv6 扩展了地址，使地址长度达到 128 位。可用 IPv6 地址的数量大得惊人（想想宇宙中的原子数量），因此我们几乎肯定永远不会耗尽 IPv6 地址。

IPv6 的设计者借此机会清理并现代化改造了 IP 首部，删除和更新了过时字段。最初，人们希望 IPv6 成为一种更具雄心的协议，包含许多新的寻址功能，但这些功能大多从未实现。实践中，除了这种“大扫除”式地移除过时功能以外，与 IPv4 相比，该协议并没有太多重大变化，因此最终得到的是一种更为优雅的 IP 协议，却没有太多雄心勃勃的改动。

注：如果你好奇的话，IPv5 于 1990 年发布（早于 1998 年的 IPv6）。它是一种从未得到广泛实现的实验性协议。

IPv6 取消了 IP 数据包首部中的校验和。支持加入校验和的论点是：如果数据包发生损坏却未被检测出来，损坏的数据包会继续传输，浪费带宽。加入校验和可以确保丢弃该数据包，避免把带宽浪费在损坏的数据包上。在现代，带宽不再是那么严重的瓶颈，因此不再需要校验和；即使有些损坏的数据包一路穿过整个网络，对性能的影响也不会太大。

IPv6 取消了分片。如果某个 IPv6 数据包对特定链路来说过大，路由器会丢弃该数据包，并把一条包含最大允许数据包大小（MTU）的错误消息发回源端。原始发送方负责将数据拆分成更小的数据包，并重新发送这些较小的数据包。终端主机（例如你的个人计算机）处理的数据包少于路由器（例如数据中心里的路由器），因此，将分片工作负载从路由器转移到终端主机能够提高互联网的整体可扩展性。

IPv6 使用经过修改的协议字段实现取代了可变长度的选项部分。在 IPv4 中，选项会产生更难解析的可变长度首部，因而存在问题。在 IPv6 中，首部长度固定。这也意味着可以取消首部长度字段。

为了继续支持选项，IPv6 对协议字段进行了泛化，使 IP 数据包可以在到达第 4 层之前向上传递以进行特殊处理。（回想一下，IPv4 中的协议首部被设为 7 或 19，用于指明接下来由哪个第 4 层协议处理数据包。）在 IPv6 中，该字段从协议改名为下一个首部（next header）。

如果希望由一个额外协议处理 IP 数据包，可以把该协议对应的编号放入下一个首部字段。这些额外协议的设计者和用户需要就各编号对应哪些协议达成一致，还需要一个标准机构管理这些编号。随后，有效载荷可以传递给额外协议；该协议能够读取一个额外首部（位于第 3 层 IPv6 首部之后、第 4 层首部之前）并进行额外处理，然后再把剩余的有效载荷传递给第 4 层。

如果数据包没有额外选项，那么下一个首部字段就与旧的协议字段相同，使 IP 数据包无需进一步处理便可直接向上传递给第 4 层协议。

下一个首部的思想可以进一步泛化，使多个协议能够在 IPv6 之后、第 4 层之前处理数据包。例如，IPv6 可以包含一个用于特殊处理的下一个首部。随后，特殊处理协议的首部也可以包含一个下一个首部字段，指定某个第 4 层协议或另一个特殊处理协议。这种方法面向未来，因为它支持尚未发明的未来协议。那些未来协议可以通过这种下一个首部的方法加入，而不会破坏 IPv6，也不需要更新 IPv6。

IPv6 在首部中增加了 流标签（flow label） 字段。在第 3 层，数据包彼此独立地发送（一个数据包如何发送不会影响其他数据包），但实践中，许多数据包通常会以某种方式相互关联。例如，在两台主机之间的视频流中，同样两个应用程序之间可能会发送许多数据包。第 3 层本应分别处理这些数据包，但实践中，路由器添加了称为 中间盒（middleboxes） 的更高级系统（例如防火墙、入侵检测系统），它们可能会关心这些数据包属于同一个流或连接这一事实。例如，防火墙可能需要读取一个连接中的多个数据包，才能决定应当允许还是阻止该连接。当所有数据包都彼此独立地发送时，这些中间盒必须猜测两个数据包是否相关（例如，它注意到数据包具有相同的源/目的 IP 地址）。IPv6 增加了一种明确表示多个数据包相互关联的方法。

IPv4 和 IPv6 的版本号字段没有变化。数据包长度字段没有变化（不过从总长度改名为有效载荷长度）。TTL 改名为跳数限制（Hop Limit），但功能没有变化。

服务类型比特改名为流量类别（Traffic Class），仍可用于实现某种数据包优先级概念。

总体而言，IPv6 接受端到端原则，并尽可能要求终端主机完成工作（分片、验证校验和以及重新发送损坏的数据包）。有些字段（例如跳数限制或 TTL）从根本上说是 IP 层的问题，无法由终端主机实现。（终端主机如何帮助处理一个正在网络中循环的数据包？）

IPv6 还试图简化首部（移除可变长度选项），同时仍为未来的改进保留可扩展性（下一个首部方法、流标签）。

IP 首部安全

IP 本身没有任何抵御攻击者的内置安全机制。攻击者可以发送一个源 IP 地址不正确的数据包，从而冒充他人。这可能导致被冒充的主机错误地为某个数据包承担责任。或者，如果攻击者发送伪造的数据包，回复可能会被发往被冒充的主机。谎报源地址称为 IP 欺骗（IP spoofing）。

IP 欺骗可用于拒绝服务（denial-of-service, DoS）攻击。DoS 攻击可以通过向服务器大量发送数据包使其不堪重负并崩溃。如果所有数据包都来自同一个发送方，服务器可以忽略来自攻击者 IP 地址的数据包，从而阻止攻击。然而，如果攻击者谎报源 IP 地址，服务器就更难区分攻击流量和合法流量。

还存在涉及欺骗的更复杂攻击，不过本课程不会详细介绍（更多细节请参阅加州大学伯克利分校 CS 161 讲义）。

IP 首部中的 ToS 字段允许发送方为自己的数据包设置优先级。如果允许所有人自行设置优先级，恶意用户就可以设置更高的优先级，欺骗网络优先处理攻击者流量。

如果网络对高优先级流量收取额外费用，攻击者可以发送伪造的高优先级数据包，而被冒充的主机将不得不为攻击者的流量付费。

最初的互联网设计并未阻止这些攻击，不过现代 ISP（互联网服务提供商，Internet service providers）已经实施了额外的安全措施，以缓解 IP 层攻击。在现代互联网中，ISP 不允许终端主机设置 ToS 字段，许多 ISP 还使用工具检测并阻止伪造的数据包。

在 IPv4 中，攻击者可以故意发送大型数据包，迫使路由器执行额外的数据包分片工作。或者，攻击者可以故意添加额外选项，迫使路由器处理这些额外选项。这可以用来发动 DoS 攻击，使路由器的处理能力不堪重负。

TTL 字段可以被用来了解网络拓扑。你可以发送一个 TTL 为 1 的数据包。该数据包会在第一跳过期，第一台路由器会向你发送一条错误消息，从而使你得知第一台路由器的身份。

接着，你可以发送一个 TTL 为 2 的数据包，它会在第二跳过期。第二台路由器会向你发送一条错误消息，使你也能发现第二台路由器。

通过使用 TTL 3、TTL 4 等不断重复这一过程，你可以发现路径上的所有路由器。这种攻击称为跟踪路由（traceroute），不过也有人认为它不是攻击，而是一种有用的诊断手段。

针对不同源端和目的端重复这种攻击，可以了解更多网络拓扑。有些路由器在 TTL 超限时不会发送错误消息，这可能会限制这种利用方式。

理论上，攻击者可以篡改协议或校验和字段，但这很可能会导致数据包因协议或校验和无效而被丢弃，因此利用这两个字段的实际攻击并不存在。
